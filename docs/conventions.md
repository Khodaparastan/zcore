# zcore Conventions

Conventions shared across all zcore modules. Follow these when adding or
extending APIs.

**Scope.** These conventions govern the files this repository owns: `zcore.zsh`,
`zbase`, `ui`, `zkv`, `zbus`, `z`, `lib/<module>/`, `bin/`, and `tests/`. `zlog`
is a [git submodule](../lib/zsh-log) with its own upstream and its own house
style; do not reformat it here.

## Return channel: `REPLY`, `reply`, `REPLY2`

Many public functions that produce values use global return channels
(documented in zbase). This is a function-level contract, not a rule that
every namespace must follow: cache reads and terminal formatters, for example,
print to stdout so they compose naturally with command substitution.

| Variable | Type | Usage |
|----------|------|-------|
| `REPLY` | scalar | Primary result; reset on entry by functions that own it |
| `reply` | array | List result; reset on entry by functions that own it |
| `REPLY2` | scalar | Secondary detail when documented |

**Rules:**

- Read return values immediately after the call, before calling another zcore function.
- Pure predicates and status-only mutators do not touch these globals unless
  their individual contract explicitly says otherwise.
- On error, a value-producing function resets its owned channel to the
  documented empty or default value.
- Emit-path `zlog` (`info`, `warn`, `error`, `debug`, `always`, `once`,
  `rate_limit`, `log`, and the `printf` variants) is **REPLY-neutral** and
  will not clobber these channels. Accessors such as `zlog::with_context`
  still return through `REPLY` by contract.

## Error codes

Defined in `zbase` (v3 verb-root namespace):

| Constant | Value | Meaning |
|----------|-------|---------|
| `Z_ERR_GENERAL` | 1 | Unspecified failure |
| `Z_ERR_INPUT` | 2 | Bad argument or state |
| `Z_ERR_NOTFOUND` | 3 | Missing resource |
| `Z_ERR_PERM` | 4 | Denied / locked |

Module-specific codes (e.g. `ZCORE_ERROR_TIMEOUT=124` in `z`) live in the module that defines them.

## Verb-root namespace (zbase v3)

Public zbase APIs use verb roots that encode return-channel contracts:

| Root | Contract |
|------|----------|
| `z::is::` | Silent predicate — branch on `$?`, never sets REPLY |
| `z::ensure::` | Guard — returns code, logs on failure, never sets REPLY |
| `z::get::` | Value query — sets `REPLY` or, where documented, `reply`/stdout |
| `z::set::` | State mutator — status only, never sets REPLY |
| `z::do::` | Effects (run, source, call) — sets REPLY only where documented |

## Naming

| Pattern | Visibility | Example |
|---------|------------|---------|
| `z::ns::name` | Public API | `z::kv::get` |
| `_z::ns::name` | Module-private | `_z::kv::epoch` |
| `__z::ns::name` | Module-private | `__z::cache::check_ttl` |
| Module-specific `_prefix_*` / `__zlog*` | Internal state | `_zkv_handles`, `_zcore_subsys` |

Namespaces use lowercase segments separated by `::`. Use verbs for actions (`get`, `set`, `emit`), nouns for accessors.

## Split-source layout

A module may be split into part files under `lib/<module>/`. **The parts are
canonical**; the single file at the repository root is a build artifact
assembled by `bin/zbundle` and carries a "Generated by bin/zbundle — do not
edit" notice. Editing the root file is always a mistake: the next
`make bundle` discards it, and `make lint`, `make install`, and
`test_bundle.zsh` all fail on the drift first.

```
lib/z/
  parts        Ordered manifest: "<part-file>  [<bundle section title>]"
  header.zsh   Head part — module banner, load guard, deps, constants
  cache.zsh    One major section per part
  ...
  z.zsh        Development loader — sources the parts in manifest order
```

Rules:

- The **manifest is the single source of truth for ordering**, read by both
  the bundler and the loader. A part that is not listed never ships.
- The **head part** is listed first and carries the full module banner; it is
  emitted verbatim. Every later part needs a section title in the manifest,
  which becomes its major divider in the assembled file.
- Parts run at **file scope** when assembled, so the loader must source them
  at file scope too — never inside a function, where a bare `typeset` would
  silently create a local instead of a global.
- The load guard belongs in **both** the head part and the loader: `return`
  inside a sourced part only leaves that part, so without its own guard the
  loader would carry on and re-assign readonly constants.
- Regenerate with `make bundle`, and verify with `make bundle-check`.

### Part file banner

Parts use the reduced field set `Description:`, `Part of:`, `Requires:`. The
bundler strips this banner and the shebang when assembling, so it documents
the part for whoever opens it, not the shipped module:

```zsh
#!/usr/bin/env zsh
# =============================================================================
# z/cache.zsh — Process-scoped cache with optional TTL
# =============================================================================
# Description:  In-memory key/value cache with absolute-expiry TTLs and
#               namespace-scoped counters.
#
# Part of:      z — assembled by bin/zbundle; see lib/z/parts
#
# Requires:     zlog; emits cache:* through z::event::* when the bus
#               subsystem is active
# =============================================================================

<body — exactly one blank line after the banner>
```

The blank line after the banner is load-bearing: the bundler skips exactly one
and keeps everything after it verbatim.

## Idempotent load guard

Every module must be safe to source twice. Guard before the first
`typeset -gr`, because re-assigning a readonly constant aborts the load:

```zsh
(( ${_zkv_loaded:-0} )) && return 0
typeset -gi _zkv_loaded=1
typeset -gri ZKV_VERSION=4
```

In `z` the guard also has to work when the file is executed rather than
sourced, hence `return 0 2>/dev/null || exit 0`. For a split module the same
guard appears in the head part and in the loader — see
[Split-source layout](#split-source-layout).

## Locating sibling files

Choose the path expression from how the file is entered. Confusing an
executed script with a sourced module makes the result depend on the caller's
working directory or script path.

| File behavior | Directory expression | Why |
| :--- | :--- | :--- |
| Sourced module or loader | `${${(%):-%x}:A:h}` | `%x` identifies the file currently being sourced |
| Executed script or test | `${0:A:h}` | `$0` identifies the executable script |

For a sourceable loader:

```zsh
typeset -g _root="${${(%):-%x}:A:h}"
source "${_root}/ui"
```

For a test file that is always executed:

```zsh
source "${0:A:h}/../../bootstrap.zsh"
```

Apply `:A` before `:h` to normalize the path and follow symlinks. Do not use
`${0:A:h}` inside a generally sourceable file: there `$0` identifies the
caller rather than the file being loaded.

## `z::result` pattern

Functions that can fail return a shell exit code and optionally populate `REPLY`/`REPLY2`:

```zsh
z::kv::get handle key || return $?
# use $REPLY
```

Callers should check `$?` before reading globals.

## Binary-safe encoding (zkv / zbus)

Field and record separators from zbase:

- `Z_SEP` (`\x01`) — field delimiter
- `Z_RECSEP` (`\x02`) — record delimiter
- `Z_ESC` (`\x03`) — escape prefix

Values containing these bytes must be encoded via `_z::kv::encode_value` / decoded on read.

## Logging

- Use `zlog::{error,warn,info,debug}` with structured key-value pairs.
- Emit-path functions leave the caller's `REPLY` / `reply` untouched.
  Accessors (`with_context`, `get_timestamp`, `benchmark_start`, …) still
  return through `REPLY`.
- Module load may use `zlog::once` to avoid duplicate startup noise.
- Tests typically call `zlog::set_level error`. Raising the log level in
  application code must change only verbosity, never return values.

## Testing

- Test functions: `test_*`, discovered by `ztest::run`.
- Hooks: `test_setup`, `test_teardown` (per test); `test_setup_all`, `test_teardown_all` (per run).
- Assertions: `ztest::assert::eq`, `ztest::assert::returns`, etc.
- Each test file runs in a subshell to isolate globals.

## Style

- `emulate -L zsh` at the start of public functions.
- Prefer `setopt extendedglob warncreateglobal typesetsilent` where the module already uses it.
- Match surrounding code; no drive-by refactors.
- Comments, banners, and section dividers follow
  [File header & comment standard](#file-header--comment-standard).

## File header & comment standard

Every zsh source file in this repository follows the layout below. It is the
single authority for banners, section dividers, and function documentation; a
reviewer should be able to reject a diff by pointing at this section alone.

All comment rules are text-only: applying them must never change behaviour.

### 1. File banner

The first line is `#!/usr/bin/env zsh` — even for files that are only ever
sourced, so editors, linters, and `file(1)` identify the language. The banner
follows immediately, with no blank line in between.

```zsh
#!/usr/bin/env zsh
# =============================================================================
# <module> — <one-line summary, capitalised, no trailing period>
# =============================================================================
# Description:  What the module is, what guarantees it makes, and anything a
#               caller must know before using it. Two to eight lines.
#
# Usage:        source zbase          # after zlog
#               z::is::file <path>
#
# Public API:   z::is::*, z::ensure::*, z::get::*
# Private API:  _z::base::*, _Z_*  (internal — no compatibility guarantee)
#
# Requires:     zlog  — structured logging; must be sourced first
#
# Provides:     Z_ERR_*, Z_SEP/Z_RECSEP/Z_ESC   (omit when the module
#               exports nothing of interest)
#
# Version:      3.0.0
# License:      MIT
# =============================================================================
```

Rules:

- Rule width is **79 columns** (`# ` plus 77 `=`), matching the 80-column limit.
- Field labels are padded so values start at **column 16**.
- Fields appear in the order shown. `Provides:` is optional; every other field
  is mandatory. Never invent new labels — extend `Description:` instead.
- `Version:` must match the version constant the module defines (`ZKV_VERSION`,
  `ZBUS_VERSION`, `_Z_BASE_VERSION`, `ZCORE_VERSION`); modules are versioned
  independently. A file with no version constant uses `./VERSION`.
- Blank comment lines (`#`) separate field groups; no blank line splits a
  single field's continuation lines.

### 2. Section dividers

Two levels only:

```zsh
# =============================================================================
# MAJOR SECTION — UPPERCASE, OPTIONAL EM-DASH QUALIFIER
# =============================================================================

# -----------------------------------------------------------------------------
# Subsection in sentence case
# -----------------------------------------------------------------------------
```

- Both rules are 79 columns. `=` is a major section, `-` a subsection; no other
  divider characters (`#####`, `─────`, `*****`) are permitted.
- Two blank lines before a major divider, one before a subsection.
- A divider may be followed by a short explanatory paragraph of `#` lines.

### 3. Function documentation

Every function is preceded by a comment block. No decorative delimiters, no
`@param`/`@return` tags — the signature line carries that information:

```zsh
# z::kv::set <handle> <key> <value> [--ttl <seconds>]
# Store a string value, replacing any existing value and its type.
# Sets REPLY to "". Returns Z_ERR_INPUT on an invalid key, Z_ERR_NOTFOUND
# when the handle is not open.
z::kv::set() {
```

- **Line 1** is the exact signature: the function name followed by its
  arguments as `<required>` and `[optional]`; `...` for variadic tails.
- **Line 2+** state the purpose in the imperative mood, then any non-obvious
  contract: which return channel is written (`REPLY`, `reply`, `REPLY2`),
  meaningful return codes, side effects, and emitted events.
- Omit what the signature already says. A three-line body needs one line of
  prose, not five.
- A run of trivial one-line predicates may share a single subsection banner
  instead of repeating a block per function.
- Private functions (`_z::*`, `__z::*`, module-specific `_prefix_*`) are documented identically;
  they have readers too.

### 4. Test files and standalone scripts

Test files and helper scripts carry the same banner with a reduced field set —
`Description:`, `Usage:`, `Covers:`, `Requires:` — and omit `Public API:`,
`Private API:`, `Version:`, and `License:`:

```zsh
#!/usr/bin/env zsh
# =============================================================================
# test_zkv_tx.zsh — Transaction semantics
# =============================================================================
# Description:  Covers begin/commit/rollback across every value type, plus
#               nesting and the discard-on-close path.
#
# Usage:        zsh tests/run_tests.zsh zkv
#               zsh tests/unit/zkv/test_zkv_tx.zsh    # standalone
#
# Covers:       z::kv::begin, z::kv::commit, z::kv::rollback
#
# Requires:     zkv — loaded by ztest::require below
# =============================================================================

source "${0:A:h}/../../bootstrap.zsh"
ztest::require zkv
```

`Requires:` names only what the suite asks for directly; `ztest::require`
resolves the prerequisites. Every suite ends with the same two lines, which
are what make it runnable on its own:

```zsh
# Standalone execution; under the runner ztest::run is called by the runner.
(( ${ZTEST_RUNNER:-0} )) || ztest::run "${1:-test_*}"
```

A `test_*` function needs a comment only when the scenario is not obvious from
its name — typically a regression test, where the comment states the defect
being guarded against. Shared helpers inside a test file are documented like
any other function — but prefer an existing `ztest::assert::*` over a local
wrapper: assertions belong to the framework, not to one file.

### Enforcement

`bin/zlint-comments` checks the mechanical half of this standard — shebang,
banner fields and their order, divider widths, comment line length, and
functions with no doc block. Run it with `make lint-style`; `make lint` runs
it alongside the `zsh -n` syntax pass and the bundle drift check.

The banner field set depends on the file: `--module` (the default) for a
module or framework, `--script` for a test file or standalone script, and
`--part` for a split-source part.

What it cannot check is whether a comment is *true*. That is a review
responsibility: a signature line that disagrees with the function body is a
worse defect than no comment at all.

### 5. Inline comments

- Explain **why**, not what: the invariant, the edge case, the reason a
  cheaper-looking alternative is wrong. Code that needs a "what" comment
  should be rewritten instead.
- Place them on their own line above the code. Trailing comments are allowed
  for short annotations, separated by at least two spaces.
- Wrap at 79 columns and start with a capital letter.
- Prefixes, used sparingly and always with a following colon: `NOTE:`,
  `SAFETY:`, `PERF:`, `TODO:`. `TODO:` must name a person or an issue.
- No commented-out code and no changelog narration ("previously this did X").
  Both belong in git history. A comment describes the code as it is today.
